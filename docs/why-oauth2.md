# 为什么选择 OAuth2

> 本文原为 README 的一个章节，因篇幅较长移至 `docs/`。它记录了 Smart-SSO 在认证协议上的取舍。

单点登录（SSO）场景下常见的技术路线有三种：传统 Token、JWT、OAuth2。下表是它们在 SSO 关注点上的对比：

| 特性 | 传统 Token | JWT | OAuth2 |
| --- | --- | --- | --- |
| 单点登录 | 支持 | 支持 | 支持 |
| 单点退出 | 支持 | 较难实现 | 支持 |
| 踢人下线 | 支持 | 较难实现 | 支持 |
| 过期续签 | 较难实现 | 支持 | 支持 |
| 性能 | 一般 | 高 | 较好 |
| 安全性 | 一般 | 较好 | 高 |
| 复杂度 | 一般 | 较高 | 高 |

## 传统 Token

机制相对简单：服务端生成一个随机字符串作为令牌，在客户端与服务端之间传递以验证用户身份。

缺点同样显著：由于缺乏时效与刷新机制，自动续签较难实现；用户从客户端发往服务端的请求需要频繁回源校验 Token。对于小型项目，尤其是性能或安全性要求不高的场景，这种方式可能已经够用。

## JWT

JWT 是无状态的，服务端只需存储密钥、无需存储令牌信息，从而减轻了服务端的存储压力。

但在 SSO 场景中，**单点退出**与**踢人下线**的实现在 JWT 下比较困难：这类功能往往需要后端存储状态，并结合注销远程通知或共享存储来达成，这与 JWT 无状态的初衷相冲突。而对部分安全性要求较高的项目来说，这两个功能是不可或缺的。

## OAuth2

OAuth2 常被用于第三方应用授权登录，同样完全适配 SSO 场景，只是实现难度相对较高：

- 天然具备令牌的**时效与刷新机制**，能够实现续签；JWT 若要达到同样效果，需改造为双 Token 方案。
- 每个需要接入认证中心的应用都必须在服务端**登记并颁发密钥**（ClientId / ClientSecret），令牌只能按流程获取。由此实现了对**用户身份**（授权码获取阶段）与**客户端应用身份**（换取 accessToken 阶段）的双重校验。
- 对于认证授权系统而言，登录成功后的首要任务是获取登录用户在当前应用内的权限，因此服务端必须**针对用户的每个客户端应用分别颁发令牌**——不能凭借某一个客户端应用拿到的令牌，去获取认证中心所管理的其它应用资源权限。这与 OAuth2 的设计初衷一致。

## 结论

Smart-SSO 选择 OAuth2 构建，并针对其不足做了针对性增强：

- **减少回源**：客户端后端缓存令牌，用户携带令牌的请求可在客户端应用本地完成校验，极大减少客户端与服务端的交互；
- **自动续签**：客户端本地令牌失效后，由客户端后端向服务端发起 refreshToken 请求，重新生成令牌并写回前端，同时延长服务端凭证存根的时效，从而实现过期自动续签；
- **可控的会话生命周期**：服务端持有全局会话（TGT），使单点退出与强制下线成为可在任意时刻触发的确定性行为。
